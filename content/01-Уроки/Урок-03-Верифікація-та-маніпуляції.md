### Слайд 3 — Верифікація даних у OSINT: навіщо це «ядро» професії

**Верифікація** — це не «перечитати ще раз пост», а **систематична перевірка**, чи відповідає твердження доступним доказам, чи коректно зібраний ланцюжок від факту до висновку.

**Чому без верифікації OSINT не існує як дисципліна:**
- **Швидкість поширення** випереджає час на роздуми: перше враження часто закріплює хибну рамку.
- **Синтетичний контент** і реюз архівних матеріалів роблять «правдоподібність» дешевою — треба окремий шар технічної й логічної перевірки.
- **Юридичні та репутаційні ризики:** помилкове звинувачення або публічний факт без джерела можуть коштувати кар’єри й довіри до всього розслідування.

**Практичний принцип уроку:** жодного «сильного» висновку без **відтворюваного** шляху: які дані, з якого джерела, яким методом перевірені.

---

### Трасування джерел (source tracing): основні поняття

**Трасування джерела** — відповідь на питання: *звідки ця інформація потрапила до мене і чи я бачу той самий артефакт, що й первинне джерело?*

| Поняття                    | Що означає в OSINT                                                                            |
| -------------------------- | --------------------------------------------------------------------------------------------- |
| **Первинне джерело**       | Оригінал події / оригінальний файл / офіційний реліз без проміжних переказів                  |
| **Вторинне джерело**       | Репортаж, тред, агрегатор, «згідно з…» — потребує звірки з первинкою                          |
| **Провенанс (provenance)** | Ланцюжок: хто, коли, де опублікував; які зміни/обрізки/скріни були між подією і твоїм архівом |
| **Триангуляція**           | Незалежні лінії доказів (геолокація + час + метадані + незалежні медіа) мають сходитися       |
| **Атрибуція**              | Хто саме стоїть за акаунтом / сайтом / «витоком» — окремий рівень впевненості                 |
|                            |                                                                                               |

**Помилка початківців:** плутати «багато постів про те саме» з **незалежними** джерелами (часто це один первинний скрін, який перепощують).

### Слайд 5 — Рівні верифікації: від «кліку» до звіту

1. **Рівень 0 — метадані та технічна автентичність:** чи файл/відео/зображення узгоджуються з заявленим місцем і часом (EXIF, тіні, ELA, C2PA тощо) — *не плутаємо з істиною змісту*.
2. **Рівень 1 — змістова перевірка:** чи твердження **логічно** випливає з цитат, таблиць, карт; чи немає підміни понять.
3. **Рівень 2 — міждокументна узгодженість:** чи новий матеріал **не суперечить** уже перевіреним фактам (contradictions, timelines).
4. **Рівень 3 — гіпотези ACH (Analysis of Competing Hypotheses):** кілька пояснень одних і тих самих спостережень + явні «дірки» в доказах.

**Висновок:** OSINT-продукт — це не скріншот, а **документований стек рішень** по цих рівнях.

---

### Слайд 6 — Якість джерела vs якість аргументації

Навіть надійне джерело може містити **слабкий аргумент**; навпаки, стиль «нейтрального експерта» не замінює **посилань на первинку**.

**Короткий чеклист аналітика:**
- [ ] Є пряме посилання / ідентифікатор оригіналу (URL, архів, хеш файлу)?
- [ ] Дата публікації **раніша** за дату поширення вірусного твердження?
- [ ] Чи збігається мова тіла доказу з мовою переказу (немає «перекладних» викривлень)?
- [ ] Чи вказано **межі невизначеності** («невідомо», «ймовірно») там, де даних бракує?

### Слайд 7 — Етика, безпека та межі верифікації

- **Розділяй:** «доказ технічної маніпуляції з файлом» і «доказ наміру конкретної особи» — це різні висновки.
- **Документуй відмови:** якщо первинку видалили — фіксуй Wayback / кеш / хеш **до** того, як слід зникне (де це дозволено).

### Слайд 8 — [ Amsterdam Matrix](https://osintforukraine.com/publications/amsterdam-matrix-handbook): мета та область застосування


**Що таке Amsterdam Matrix :**
- Рамка для **систематичної оцінки достовірності** OSINT-матеріалів (оригінально — пости в Twitter/X; методологія переноситься на треди, Telegram-експорти, блоги, «розслідувальні» ).
- Мета — **не «вподобайка»**, а **прозора таблиця ознак**, за якою двоє аналітиків можуть порівняти результати.
- Матриця допомагає відокремити **силу доказової бази** від **харизми автора** або кількості репостів.

**Зв’язок зі слайдами 3–6:** Matrix — це закріплений на папері спосіб пройти рівні верифікації та трасування джерел для *одного* артефакту (посту).

### Слайд 9 — Amsterdam Matrix: шкала 1 / 0 / −1 і кольорова логіка

Згідно з handbook, кожен з **23 параметрів** отримує код:

| Код | Зміст (узагальнено з PDF) |
|-----|---------------------------|
| **1** | Ознака **присутня і надійна** / практика відповідає best practice |
| **0** | **Невизначено**, неповні дані, або неможливо перевірити з відкритих матеріалів |
| **−1** | Ознака **відсутня**, **слабка**, або вказує на ризик маніпуляції / низьку якість |

**Візуалізація в матеріалі PDF:** «холодні» кольори для сильних сторін, «гарячі» — для ризиків, сірий — для прогалин. Це **швидкий heatmap-профіль** поста перед глибоким технічним аналізом.

### Слайд 10 — Amsterdam Matrix: кластер *Inclusion criteria*

**Питання кластера (логіка PDF):** чи матеріал взагалі підпадає під **осмислену** OSINT-перевірку і чи додає він **новий** інсайт, а не лише емоцію.

**Типові підкритерії (перевіряй по формулюваннях у PDF):**
- чи є **конкретне, фальсифіковане/підтверджуване** твердження (а не загальна думка);
- чи автор додає **оригінальні дані** (координати, таблицю, файл), а не лише пересказ чужого скріну;
- чи не є пост **чистим реагуванням** без нового факту.

**Практика:** якщо тут переважно `0` / `−1` — подальші 23 параметри часто **не врятують** слабкий матеріал; краще зупинитись і шукати первинку.

---

### Слайд 11 — Amsterdam Matrix: *Data / information / source integrity*

**Питання:** чи **прозорий ланцюжок джерела** і чи немає прихованого шуму/підміни.

**Що оцінюємо :**
- наявність **прямих посилань**, архівів, згадок первинних медіа;
- **авторство** та анотації (хто зібрав, де знайдено файл);
- відсутність **штучного шуму** (зайві емодзі, «threadreader» без посилання на оригінал);
- ознаки **маніпуляції даними** (обрізаний скрін, переклад без оригіналу, «стислий» контекст).

---

### Слайд 12 —[ Amsterdam Matrix](https://osintforukraine.com/publications/amsterdam-matrix-handbook): *Argumentation quality*

**Питання:** чи **аргумент** витримує перевірку логікою й методом.

**Орієнтири з handbook:**
- чи видно **метод** (як зібрано дані, які припущення);
- чи є **реплікованість** (інший аналітик може повторити кроки);
- чи автор **чесно позначає невідоме** замість заповнення прогалин здогадками;
- чи немає **підміни кореляції на причинність**.

**Пам’ятай:** сильна аргументація не компенсує фейкового **первинного файлу** — тому кластер *Data / information / source integrity* (слайд 11) залишається обов’язковим.

### Слайд 13 — Amsterdam Matrix: *Communication style* + *Community layer*

**Communication style (узагальнено):**
- мінімум **маніпулятивних** прийомів (залякування, «us vs them» замість фактів);
- відсутність **gaslighting** аудиторії («всі брешуть, крім мене») без даних.

**Community layer (узагальнено):**
- коректне використання **OSINT-термінів** і інструментів (не «геолокація по тіні хмари» без пояснення);
- залучення **репутаційних third parties** (хто підтвердив, чи є peer review у спільноти);
- **органічний** engagement vs ознаки координованої накачки.

**Ключовий висновок PDF (важливо для студентів):** доброзичливий стиль **не дорівнює** правоті — вирішальним лишається поєднання **integrity + argumentation**.

### Слайд 14 — MindsDB: що це, встановлення, роль у OSINT

**MindsDB** — це «AI-шар» над різними джерелами даних: ти підключаєш файли, API, бази, а далі працюєш **єдиною мовою SQL** + **агентами**, які відповідають природною мовою поверх таблиць.

**Чому це важливо саме для OSINT-розслідувань:**
- **Таблична форма** (час, джерело, сутність, статус перевірки, санкційний список тощо) — це мова, якою керівники й партнери найлегше порівнюють прогрес.
- **Розмова з даними** (AI Agent / chat over data) прискорює exploratory analysis: «які дати випадають?», «де дублікати?», «який топ джерел?» — за умови ручної перевірки висновків.
- **Федерація:** кілька таблиць / конекторів у одному запиті без написання окремого бекенду.

**Як швидко підняти локально (Docker, Linux / macOS):**
```bash
docker pull mindsdb/mindsdb
docker run -d --name mindsdb -p 47334:47334 mindsdb/mindsdb
```
Далі відкрий **MindsDB Studio:** `http://127.0.0.1:47334`. Детальніший сценарій разом із Arkham — у матеріалі курсу [[Гайд-Docker-MindsDB-та-ArkhamMirror]].

**Примітка:** для агентів потрібен налаштований LLM (ключ або локальний endpoint) згідно документації MindsDB; у публічних скріншотах не показуй секрети.

### Слайд 19 — MindsDB: таблиці, SQL і «розмова» з доказовою базою

**Типовий OSINT-пайплайн у MindsDB:**
1. **Ingest / upload** дозволеного датасету (наприклад, відкриті санкційні списки, агрегований таймлайн подій, експорт метаданих) у віртуальну базу MindsDB.
2. **SQL** для контрольних зрізів: кількість записів за джерелом, вікно дат, статуси верифікації.
3. **Agent / chat** для інтерпретації та гіпотез — **завжди** з повторною перевіркою первинних документів у Arkham або в оригінальному джерелі.

**Чому «просто Excel» недостатньо:** MindsDB тримає **живі** конектори до БД (у т.ч. до PostgreSQL Arkham у лабораторних сценаріях) і дозволяє повторно виконувати ті самі запити, коли корпус оновився після нового ingest.

### Слайд 20 — Реальні SQL приклади: MindsDB читає ArkhamMirror

```sql
-- 1) Статус ingestion jobs
SELECT status, COUNT(*) AS jobs
FROM arkham_pg.arkham_ingest.jobs
GROUP BY status
ORDER BY jobs DESC;

-- 2) Останні 5 ingest jobs
SELECT id, filename, status, created_at
FROM arkham_pg.arkham_ingest.jobs
ORDER BY created_at DESC
LIMIT 5;

-- 3) Документи по проєктах Arkham
SELECT
  p.name AS project_name,
  COUNT(d.id) AS docs,
  COALESCE(SUM(d.file_size), 0) AS total_bytes
FROM arkham_pg.arkham_frame.projects p
LEFT JOIN arkham_pg.arkham_frame.documents d ON d.project_id = p.id
GROUP BY p.name
ORDER BY docs DESC;
```

**Що це дає аналітику OSINT:**
- миттєво бачиш обсяг оброблених матеріалів;
- контролюєш ingest-потік без окремих скриптів;
- будуєш комбіновані зрізи (проєкт + документи + jobs) в одному SQL-запиті.

### Слайд 22 — MindsDB як MCP-сервер для зовнішніх агентів

**Model Context Protocol (MCP)** — відкритий стандарт, яким користуються IDE та автономні агенти, щоб безпечно викликати **інструменти** (tools) замість «галюцинованого SQL».

**Роль MindsDB у цій схемі:** MindsDB може виступати **MCP-сервером**, через який зовнішній агент (Claude Desktop, Cursor, кастомний оркестратор) отримує можливість:
- перелічити підключені бази / джерела;
- виконувати **federated query** поверх уже налаштованих інтеграцій;
- повертати результати в структурованому вигляді для наступних кроків розслідування.

**Офіційна документація (оновлюється разом із релізами):** [Model Context Protocol (MCP) — MindsDB](https://docs.mindsdb.com/model-context-protocol/overview) та розділ **Usage** в тій самій документації.

**Практичний сенс для курсу:** ArkhamMirror залишається **канонічним місцем** для документів і верифікаційних шардів, MindsDB — **SQL + MCP-шлюз**, через який інші AI-агенти можуть читати **табличні** зрізи стану розслідування, не переписуючи інтеграції під кожен інструмент.

### Слайд 25 — Три типи маніпуляцій

| Тип | Визначення | Умисел | Для OSINT |
|-----|-----------|--------|-----------|
| **Misinformation** | Хибна інформація без злого умислу | Немає | Поширюється добросовісно |
| **Disinformation** | Навмисно створена хибна інформація | Є | Скоординована операція |
| **Malinformation** | Справжня інформація вжита для шкоди | Є | **Найнебезпечніша** — детектори не спрацюють |

**Malinformation в практиці:**
- Реальна фотографія катастрофи + неправильне місце і дата
- Справжній документ вирваний з контексту
- Реальна цитата без першоджерела та навколишнього контексту

**Що варто винести в контекст нашого курсу:**

- **Case Manager агенти** — гіпотези, пошук по базах і вебу, візуалізація вузлів і зв’язків; **Hypothesis Modeling** — перехід від перевірених даних до **захищеної наративної моделі** для суду / регулятора / ради директорів.

### Слайд 26 — [SHATTERED](https://github.com/mantisfury/ArkhamMirror) (ArkhamMirror): статус проєкту та ідея

**Важливо про зрілість:** ArkhamMirror / SHATTERED — **дуже свіжий** open-source проєкт, фактично **рання beta**: змінюються ендпоінти, назви полів, поведінка воркерів і UI. Для курсу це **плюс**: ми дивимося на **архітектурні ідеї**, які рідко зібрані в одному місці, а не на «заморожений enterprise-продукт».

**Що саме варто винести навіть попри beta:**
- **Voltron-модель:** ядро (**ArkhamFrame**) + підключаючі **шарди** — кожен модуль ізольований, залежить лише від ядра.
- **Подієва бус  (EventBus):** шарди не імпортують один одного напряму — з’єднання через події → менше крихких залежностей.
- **Єдиний корпус даних:** PostgreSQL + pgvector + черги jobs — зручно для **трасування** (що коли обробили) і для зовнішньої аналітики (наприклад, MindsDB поверх тих самих таблиць).

**Архітектура (спрощено):**
```
┌─────────────────────────────────────────┐
│           ArkhamFrame (ядро)            │
│  PostgreSQL · pgvector · EventBus       │
└────────────────┬────────────────────────┘
                 │
    ┌────────────┼────────────┐
    ▼            ▼            ▼
 [шарди: claims, media-forensics, ach, …]   ← повний перелік: слайди 28–29 (атлас шардів, дві частини)
                 │
    ┌────────────┼────────────┐
    ▼            ▼            ▼
  React UI   REST API   EventBus
  :8100      /docs      pub/sub
```

### Слайд 27 — Архітектурні концепти ArkhamMirror (що «означає» дизайн)

| Концепт                           | Що це дає OSINT-команді                                                                             |     |
| --------------------------------- | --------------------------------------------------------------------------------------------------- | --- |
| **Frame = незмінне ядро**         | Стабільні сервіси БД, векторів, LLM, воркерів; шарди не «ломають» платформу випадковими патчами.    |     |
| **Shard = функціональний модуль** | Можна ввімкнути/вивчити лише потрібне для кейсу (наприклад, спочатку `ingest` + `claims`).          |     |

| **Job queue**                     | Важкі кроки (OCR, embed, парсинг) — асинхронно; аналітик бачить **стан** обробки, а не «зависання». |     |
| **Проєкти (`projects`)**          | Ізоляція корпусів доказів між кейсами — критично для керованості та експорту.                       |     |

### Слайд 37 — Шард Contradictions: Виявлення суперечностей

**Що робить:** порівнює документи між собою, знаходить суперечливі твердження через векторні ембедінги + LLM-верифікацію.

**Типи суперечностей:**
| Тип | Приклад |
|-----|---------|
| `direct` | Документ А: "загинуло 5" / Документ Б: "загинуло 50" |
| `temporal` | Різні дати однієї і тієї ж події |
| `quantitative` | Числові розбіжності |
| `causal` | Конфлікт причинно-наслідкових зв'язків |
| `attributive` | "Це сказав X" vs "це сказав Y" |

**Severity рівні:** `critical` → `high` → `medium` → `low`

### Слайд 39 — Contradictions: Batch та Chain аналіз

**Крок 2 — Batch аналіз кількох пар (3+ документи):**
```bash
curl -X POST http://localhost:8100/api/contradictions/batch \
  -H "Content-Type: application/json" \
  -d '{
    "document_pairs": [
      ["doc_A", "doc_B"],
      ["doc_A", "doc_C"],
      ["doc_B", "doc_C"]
    ],
    "async_mode": false,
    "use_llm": true
  }'
```

**Async режим для великих корпусів:**
```bash
# async_mode: true → повертає job_ids замість результатів
# Статус перевіряється: GET /api/contradictions/jobs/{job_id}
```

**Chain Detection** — знаходить ланцюги суперечностей:
```
doc_A суперечить doc_B
doc_B суперечить doc_C
→ Chain: A → B → C (пов'язані суперечності)
→ Chain severity: critical
```

**Крок 3 — Перегляд у UI:**
SHATTERED → Contradictions → вибери матрицю → кольорове маркування:
- 🔴 Critical / 🟠 High / 🟡 Medium / 🟢 Low

**Крок 4 — Зміна статусу:**
```bash
# Підтвердити суперечність
curl -X PUT http://localhost:8100/api/contradictions/{cont_id}/status \
  -H "Content-Type: application/json" \
  -d '{"status": "confirmed", "notes": "Верифіковано через InVID"}'

# Відхилити (false positive)
curl -X PUT http://localhost:8100/api/contradictions/{cont_id}/status \
  -H "Content-Type: application/json" \
  -d '{"status": "dismissed", "notes": "Різні часові пояси — не суперечність"}'
```

**Крок 5 — Автоматичне виявлення ланцюгів:**
```bash
curl -X POST http://localhost:8100/api/contradictions/detect-chains \
  -H "Content-Type: application/json" \
  -d '{"min_chain_length": 2}'
# → знаходить A→B→C ланцюги між документами
```

### Слайд 51 — Credibility: Deception Detection (MOM/POP/MOSES/EVE)

**Інтелідженс-стандарт для детекції обману:**

**MOM — Motive, Opportunity, Means:**
```
Motive: Чи є мотив для обману?
→ "Так: операція впливу для дискредитації ЗСУ"

Opportunity: Чи була можливість сфабрикувати?
→ "Так: deepfake генерація доступна"

Means: Чи є засоби для обману?
→ "Так: досвід у диспропаганді"
```

**POP — Past Opposition Practices:**
Чи використовувало це джерело раніше подібні техніки обману?

**MOSES — Multiple, Orthogonal Sources:**
Чи підтверджується інформація незалежними джерелами без спільного кореня?

**EVE — Evaluation of Evidence:**
Якість доказів: чи можна їх підробити? Чи вони специфічні? Чи перевіряються?

### Слайд 54 — Шард ACH: Analysis of Competing Hypotheses

**ACH** — стандарт розвідувального аналізу (Richards J. Heuer Jr., CIA).

**Ідея:** замість доведення однієї гіпотези — систематично оцінювати всі можливі гіпотези проти кожного доказу.

**Рейтинги відповідності:**
| Рейтинг | Символ | Значення |
|---------|--------|---------|
| `++` | Сильно підтверджує | Доказ сильно вказує на гіпотезу |
| `+` | Підтверджує | Доказ узгоджується з гіпотезою |
| `N` | Нейтральний | Доказ не відноситься |
| `-` | Суперечить | Доказ проти гіпотези |
| `--` | Сильно суперечить | Доказ різко суперечить |
| `NA` | Не застосовно | Доказ нерелевантний |

---

### Слайд 55 — ACH: Створення матриці верифікації

**Сценарій:** верифікуємо відео з Telegram — "Азов стратив полонених"

**Гіпотези:**
- H1: Відео справжнє і знято у Херсоні 2025
- H2: Відео архівне (інший конфлікт, інший рік)
- H3: Відео deepfake
- H4: Відео справжнє але неправильний контекст

**ACH API — 4 окремих кроки (матриця → гіпотези → докази → рейтинги):**

**Крок 1 — Створи матрицю:**
```bash
MATRIX=$(curl -s -X POST http://localhost:8100/api/ach/matrix \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Верифікація: відео Telegram 2025-03-15",
    "description": "Чи є дане відео автентичним і чи відповідає заявленому контексту?"
  }' | jq -r '.matrix_id')

echo "Matrix: $MATRIX"
```

**Крок 2 — Додай кожну гіпотезу окремо:**
```bash
# H1
H1=$(curl -s -X POST http://localhost:8100/api/ach/hypothesis \
  -H "Content-Type: application/json" \
  -d "{\"matrix_id\": \"$MATRIX\", \"title\": \"Відео справжнє, Херсон 2025\"}" | jq -r '.hypothesis_id')

# H2
H2=$(curl -s -X POST http://localhost:8100/api/ach/hypothesis \
  -H "Content-Type: application/json" \
  -d "{\"matrix_id\": \"$MATRIX\", \"title\": \"Відео архівне (інший конфлікт)\"}" | jq -r '.hypothesis_id')

# H3
H3=$(curl -s -X POST http://localhost:8100/api/ach/hypothesis \
  -H "Content-Type: application/json" \
  -d "{\"matrix_id\": \"$MATRIX\", \"title\": \"Відео deepfake\"}" | jq -r '.hypothesis_id')

# H4
H4=$(curl -s -X POST http://localhost:8100/api/ach/hypothesis \
  -H "Content-Type: application/json" \
  -d "{\"matrix_id\": \"$MATRIX\", \"title\": \"Справжнє але хибний контекст\"}" | jq -r '.hypothesis_id')
```

### Слайд 56 — ACH: Додавання доказів і рейтингів

**Крок 3 — Додай докази (окремими запитами):**
```bash
# Доказ 1: TinEye знайшов відео 2019 року
E1=$(curl -s -X POST http://localhost:8100/api/ach/evidence \
  -H "Content-Type: application/json" \
  -d "{
    \"matrix_id\": \"$MATRIX\",
    \"description\": \"TinEye: перша поява відео 2019-07-22, джерело Reuters, Кабул\",
    \"evidence_type\": \"fact\",
    \"source\": \"TinEye reverse image search\",
    \"credibility\": 0.9
  }" | jq -r '.evidence_id')

# Доказ 2: Мова у відео — арабська
E2=$(curl -s -X POST http://localhost:8100/api/ach/evidence \
  -H "Content-Type: application/json" \
  -d "{
    \"matrix_id\": \"$MATRIX\",
    \"description\": \"Аудіо аналіз: мова у відео арабська, не українська\",
    \"evidence_type\": \"fact\",
    \"credibility\": 0.85
  }" | jq -r '.evidence_id')
```

**Крок 4 — Виставляй рейтинги (окремо для кожної пари доказ×гіпотеза):**
```bash
# E1 vs H1: TinEye 2019 сильно суперечить "Херсон 2025"
curl -X PUT http://localhost:8100/api/ach/rating \
  -H "Content-Type: application/json" \
  -d "{\"matrix_id\": \"$MATRIX\", \"evidence_id\": \"$E1\", \"hypothesis_id\": \"$H1\", \"rating\": \"--\"}"

# E1 vs H2: підтверджує "архівне відео"
curl -X PUT http://localhost:8100/api/ach/rating \
  -H "Content-Type: application/json" \
  -d "{\"matrix_id\": \"$MATRIX\", \"evidence_id\": \"$E1\", \"hypothesis_id\": \"$H2\", \"rating\": \"++\"}"

# E1 vs H3: нейтральний для deepfake
curl -X PUT http://localhost:8100/api/ach/rating \
  -H "Content-Type: application/json" \
  -d "{\"matrix_id\": \"$MATRIX\", \"evidence_id\": \"$E1\", \"hypothesis_id\": \"$H3\", \"rating\": \"N\"}"

# E2 vs H1: арабська мова суперечить Херсону
curl -X PUT http://localhost:8100/api/ach/rating \
  -H "Content-Type: application/json" \
  -d "{\"matrix_id\": \"$MATRIX\", \"evidence_id\": \"$E2\", \"hypothesis_id\": \"$H1\", \"rating\": \"--\"}"
```

**Рейтинги:** `++` (сильно підтверджує) / `+` / `N` (нейтральний) / `-` / `--` (сильно суперечить) / `NA`

**Крок 5 — Розрахуй бали:**
```bash
curl -X POST "http://localhost:8100/api/ach/score?matrix_id=$MATRIX"
# → scores з rank для кожної гіпотези
# Менший weighted_score = менш несумісна з доказами = більш ймовірна
```

### Слайд 59 — ACH: Корпусний пошук доказів

**Corpus Search** — SHATTERED шукає докази для ACH матриці прямо у завантажених документах:

```bash

    \"limit\": 10
  }"
```

**Результат:** SHATTERED знаходить документи у проєкті що можуть слугувати доказами → пропонує їх додати до матриці.

**Прийняти запропоновані докази:**
```bash

  -H "Content-Type: application/json" \

  }"
```

**Пошук по всьому корпусу (не один запит):**
```bash

  -d "{\"matrix_id\": \"$MATRIX\"}"
# → шукає докази для ВСІХ гіпотез автоматично
```

**Практичний workflow:**
1. Завантажив 50 документів у проєкт
2. Створив матрицю + гіпотези
3. `corpus-search-all` → SHATTERED знаходить релевантні докази серед 50 документів
4. Приймаєш відібрані, виставляєш рейтинги вручну або через `ai/ratings`
5. `score` + `ai/insights` → висновок

### Слайд 60 — ACH: Повна схема роботи з API

```
┌──────────────────────────────────────────────────────────────┐
│                    ACH Workflow (SHATTERED)                  │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│  POST /api/ach/matrix                                        │
│  └── {"title": "...", "description": "..."}                  │
│      → matrix_id                                             │
│                                                              │
│  POST /api/ach/hypothesis  (×N разів)                        │
│  └── {"matrix_id": "...", "title": "H1: ..."}               │
│      → hypothesis_id (H1, H2, H3, ...)                       │
│                                                              │
│  POST /api/ach/evidence  (×M разів)                          │
│  └── {"matrix_id": "...", "description": "E1: ..."}         │
│      → evidence_id (E1, E2, ...)                             │
│                                                              │
│  PUT /api/ach/rating  (×N×M разів)                           │
│  └── {"matrix_id", "evidence_id", "hypothesis_id",          │
│       "rating": "++" | "+" | "N" | "-" | "--" | "NA"}       │
│                                                              │
│  POST /api/ach/score?matrix_id=...                           │
│  └── розраховує weighted inconsistency score                 │
│      → ranked hypotheses (менший score = більш ймовірна)    │
│                                                              │
│  POST /api/ach/ai/insights     → узагальнення               │
│  POST /api/ach/ai/premortem    → failure modes               │
│  POST /api/ach/ai/devils-advocate → blind spots              │
│  POST /api/ach/ai/corpus-search   → auto-find evidence      │
│                                                              │
│  GET  /api/ach/export/{matrix_id} → JSON звіт               │
└──────────────────────────────────────────────────────────────┘
```

**Ключова відмінність від "старого" підходу:**
- Матриця, гіпотези, докази і рейтинги — **окремі ресурси** (REST-CRUD)
- Порядок: спочатку матриця → потім гіпотези → потім докази → потім рейтинги
- AI функції — окремі ендпоінти, не вбудовані в CRUD
- `score` рахується після виставлення рейтингів (не автоматично)

### Слайд 75 — Обмеження SHATTERED і що робити

| Обмеження                                 | Ситуація                          | Рішення                                                                                                            |
| ----------------------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Без LLM Claims і ACH не працюють повністю | Немає API ключа                   | LM Studio + Llama 3.1 8B (безкоштовно, локально)                                                                   |

| C2PA тільки для нових камер/Adobe         | Старе фото                        | C2PA absence ≠ фейк                                                                                                |

| Мова: англійська краща для NER            | Ukrainомовний текст               | Встанови [`uk_core_news_sm`](https://huggingface.co/spacy/uk_core_news_sm) або перекладай через LLM перед аналізом |

### Слайд 76 — Чеклист верифікації з SHATTERED

```
□ Проєкт створено в SHATTERED
□ Документи/зображення/відео завантажені

MEDIA FORENSICS (зображення)
□ POST /media-forensics/analyze {"document_id": "..."} запущено
□ EXIF flags перевірено (GPS, дата, ПЗ, C2PA — всі в одному аналізі)
□ ELA: POST /media-forensics/ela {"analysis_id": "..."} виконано
□ Sun position перевірено (якщо є GPS)
□ Reverse search: POST /media-forensics/similar {"analysis_id": "...", "search_type": "both"}
□ AI Junior Analyst запущено (якщо є підозри)

CLAIMS (текст)
□ POST /claims/extract-from-document/{doc_id} виконано (або /claims/extract з текстом)
□ Кожне твердження статус призначений
□ Докази прив'язані до key claims

CONTRADICTIONS (кілька документів)
□ /contradictions/analyze для всіх пар
□ Critical/High суперечності розслідувані
□ Статуси оновлені (confirmed/dismissed)

CREDIBILITY (джерело)
□ /credibility/assessments створено
□ MOM/POP/MOSES/EVE чеклист заповнено
□ Рівень: unreliable / low / medium / high / verified

ACH (гіпотези)
□ POST /ach/matrix → matrix_id
□ POST /ach/hypothesis (×N) → H1, H2, H3...
□ POST /ach/evidence (×M) → E1, E2...
□ PUT /ach/rating (×N×M) → рейтинги виставлено
□ POST /ach/score?matrix_id=... → бали розраховано
□ POST /ach/ai/insights → leading hypothesis визначено
□ POST /ach/ai/premortem → failure modes перевірено
□ POST /ach/ai/devils-advocate → blind spots перевірено

ФІНАЛ
□ Рейтинг A/B/C/D визначено
□ Звіт /api/reports або /api/export
□ Provenance chain збережено
```

### Слайд 80 — Типові помилки при роботі з SHATTERED

| Помилка | Симптом | Рішення |
|---------|---------|---------|
| LLM не налаштований | Claims extraction порожня | Перевір LLM_ENDPOINT у .env |
| Workers не запущені | Jobs застрягли у "pending" | `python -m arkham_frame.workers.cli --tier recommended` |
| pgvector не встановлений | Semantic search не працює | `CREATE EXTENSION vector;` у PostgreSQL |
| Файл > 50MB | Upload 413 error | Налаштуй `MAX_FILE_SIZE` або стисни файл |
| spaCy не встановлений | NER entities порожні | `python -m spacy download en_core_web_sm` |
| Тільки Docker але немає GPU | OCR повільний | Використовуй `paddle_only` mode або Cloud VLM |
| ACH score все нулі | Рейтинги не виставлені | `PUT /ach/rating` для кожної пари evidence×hypothesis, потім `POST /ach/score` |
| ELA повертає 503 | Pillow не встановлений | `pip install Pillow` в середовищі frame |
| C2PA `signature_valid: false` | Немає trust anchors | Встанови `MEDIA_FORENSICS_TRUST_ANCHORS_PATH` або ігноруй (manifest parsing все одно працює) |

**Швидка діагностика:**
```bash
# Стан всіх шардів
curl http://localhost:8100/api/shards | jq '.[].status'

# Помилки в queue
curl http://localhost:8100/api/ingest/queue | jq '.failed'

# Логи
docker compose logs -f app | grep ERROR
```

### Слайд 81 — Підсумок: SHATTERED у верифікаційному pipeline

**10 ключових тезисів:**

1. **SHATTERED** — єдина платформа де media forensics, claims, contradictions, credibility і ACH пов'язані між собою
2. **Media Forensics**: EXIF + ELA + GPS + C2PA + Sun position в одному ендпоінті
3. **Claims**: формалізований трекінг кожного твердження з доказами і статусами
4. **Contradictions**: автоматичний пошук конфліктів між документами через embeddings + LLM
5. **Credibility MOM/POP/MOSES/EVE**: інтелідженс-стандарт реалізований як API
6. **ACH**: структурований метод замість підтвердження однієї гіпотези
7. **Provenance**: аудит-траса кожного висновку — юридично і журналістськи надійно
8. **EventBus**: шарди реагують на події одне одного (media → claims → contradictions)
9. **Offline mode**: для чутливих розслідувань без зовнішніх API
10. **REST API**: будь-який скрипт або інструмент може надсилати дані у SHATTERED
