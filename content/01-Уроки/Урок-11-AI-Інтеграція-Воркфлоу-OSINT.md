## Вступ: де аналітик витрачає час — і де його бере AI

Більшість OSINT-аналітиків витрачають на **реальний аналіз** лише близько 12% робочого часу. Решта йде на механічну роботу:

```
Збір даних                  ████████████████  35%
Переклад / нормалізація     ████████          18%
Написання звіту             ████████████      25%
Пошук по нотатках           ████              10%
Реальний аналіз             ████              12%
```

AI здатний забрати на себе більшу частину цієї механічної роботи — але тільки якщо аналітик розуміє, що саме він делегує і чому. Цей урок — про те, як збудувати такий процес.

**Де AI бере на себе тягар:**
- Переклад і перефразовування → LLM
- Структурування чернеток звіту → LLM
- Генерація коду для скрейпінгу/парсингу → LLM
- Автоматичні графіки з даних → Python + LLM
- Пошук по накопичених нотатках → векторна БД + RAG

**Де AI не замінює аналітика:**
- Оцінка достовірності джерела
- Атрибуція: хто стоїть за операцією
- Ключові судження з юридичними або оперативними наслідками
- Рішення під невизначеністю на основі досвіду

> **Принцип уроку:** AI підвищує якість роботи аналітика — але лише якщо аналітик розуміє, що саме він делегує і чому.

## Частина І — Розвідувальний звіт: стандарти та AI

Більшість OSINT-аналітиків вміють збирати інформацію. Набагато менше вміють перетворювати її на аналітичний продукт, що реально допомагає приймати рішення. У цій частині — стандарти, без яких звіт залишається лише набором фактів.

### Планування перед написанням

**«Справжня цінність — не в тому, що ви знайшли, а в тому, як ви це інтерпретували.»**
*(Dutch OSINT Guy)*

Перш ніж відкривати редактор, дайте відповідь на три питання:

**1. Яка мета продукту?**
- Попередити про загрозу → Flash report
- Підтвердити або спростувати гіпотезу → Assessment
- Надати фактологічну базу для рішення → Strategic estimate
- Задокументувати знахідку для юридичних цілей → Forensic report

**2. Хто аудиторія?**

| Аудиторія | Що їм потрібно |
|-----------|----------------|
| **Технічний фахівець** | Деталі методології, сирі метрики, відтворюваність |
| **Керівник / замовник** | Ключові висновки, ризики, рекомендовані дії |
| **Юрист / суд** | Ланцюжок доказів, цитування джерел, нейтральна мова |
| **Медіа / громадськість** | Доступна мова, без жаргону, наочні візуалізації |

**3. Яке рішення буде прийнято на основі цього звіту?**

Якщо відповідь незрозуміла — уточніть у замовника перед початком роботи. Звіт без зрозумілого замовника не має аналітичної цінності.

> **Промпт для Claude (допомога з плануванням):**
> *«Я пишу OSINT-звіт для [тип аудиторії] з метою [ціль]. Яка структура найбільш підходить? Які деталі включити, які опустити? Які терміни потребують пояснення для цієї аудиторії?»*

### Анатомія розвідувального звіту

**Розвідувальний продукт (Intelligence Product)** — структурований документ, що перетворює сирі дані на знання, придатне для прийняття рішень.

**Повна структура (7 секцій):**

```
┌─────────────────────────────────────────────┐
│  1. ТИТУЛЬНА СТОРІНКА                       │
│     Назва · Організація · Дата · Гриф ·     │
│     Номер кейсу                             │
├─────────────────────────────────────────────┤
│  2. BLUF (Bottom Line Up Front)             │  ← 1–3 речення
│     Ключове судження + рівень впевненості   │
├─────────────────────────────────────────────┤
│  3. ВСТУП                                   │
│     Цілі · Обсяг · Дослідницькі питання ·  │
│     Значущість для замовника                │
├─────────────────────────────────────────────┤
│  4. МЕТОДОЛОГІЯ                             │  ← прозорість
│     Інструменти · Джерела · Обмеження ·    │
│     Процес верифікації                      │
├─────────────────────────────────────────────┤
│  5. ЗНАХІДКИ (Findings)                     │
│     Хронологічно або тематично              │
│     Факти відокремлені від оцінок           │
├─────────────────────────────────────────────┤
│  6. АНАЛІЗ                                  │
│     Key Judgements + рівні впевненості ·   │
│     Патерни · Альтернативні сценарії ·     │
│     Прогалини в інформації                  │
├─────────────────────────────────────────────┤
│  7. ВИСНОВКИ ТА РЕКОМЕНДАЦІЇ               │
│     Конкретні · Дієві · Пріоритизовані     │
└─────────────────────────────────────────────┘
```

**Типи розвідувальних продуктів:**

| Тип | Обсяг | Призначення |
|-----|-------|-------------|
| **Flash report** | 1 абзац | Термінове попередження, до 2 годин |
| **Spot report** | 1 сторінка | Подія або знахідка |
| **Assessment** | 2–5 сторінок | Поглиблений аналіз теми |
| **Strategic estimate** | 10–20+ сторінок | Довгостроковий прогноз |

### BLUF: як писати перший абзац

**BLUF (Bottom Line Up Front)** — ключовий принцип розвідувального письма. Найважливіший висновок — першою фразою. Завжди.

**Чому BLUF важливий:**
- Керівник читає перший абзац і вирішує, чи потрібно читати далі
- Якщо висновок похований у кінці — він може бути пропущений
- Якщо не можеш написати BLUF — аналіз ще не завершений

**Структура BLUF:**
```
[Ключовий висновок] + [Рівень впевненості] + [Найважливіший факт-обґрунтування]
```

**Погано (Bottom Line at the Bottom):**
> «Ми проаналізували активність 47 Telegram-каналів за 6 місяців. Загальна кількість повідомлень склала 1.2 мільйони. Серед них виявлено повторюваний контент. Час публікацій корелює між каналами. З урахуванням усього вищезазначеного, вважаємо за можливе припустити наявність координації.»

**Добре (BLUF):**
> «З високою впевненістю оцінюємо, що 10 із 47 досліджуваних Telegram-каналів діють як координована мережа — публікують ідентичний контент у вікні ±5 хвилин із синхронізацією учасницької бази 78–91%.»

**Підказка від AI:** Після написання чернетки попросіть Claude:
> *«Перепиши перший абзац цього звіту у форматі BLUF: ключове судження першою фразою, рівень впевненості явно вказаний, жодної передісторії до ключового висновку.»*

### Рівні впевненості та мова оцінок

**Рівні впевненості** — стандартизована шкала, що дозволяє читачу розуміти, наскільки аналітик впевнений у судженні. Відсутність явного рівня впевненості — це аналітична помилка, а не нейтральність.

**Три рівні (стандарт розвідувального аналізу):**

| Рівень | Формулювання | Коли застосовувати |
|--------|-------------|-------------------|
| **Висока впевненість** | *«з високою впевненістю оцінюємо»* | Чисельні докази, кілька незалежних джерел, логічно несуперечлива картина |
| **Помірна впевненість** | *«оцінюємо»*, *«вважаємо ймовірним»* | Деякі докази, але є прогалини або альтернативні пояснення |
| **Низька впевненість** | *«допускаємо»*, *«не можемо виключити»* | Мало даних, одне джерело, значна невизначеність |

**Мова ймовірності:**

| Слово | Ймовірність |
|-------|------------|
| Майже напевно / практично безсумнівно | > 95% |
| Очевидно / з великою ймовірністю | 75–95% |
| Ймовірно / схоже | 55–75% |
| Приблизно рівна ймовірність | 45–55% |
| Малоймовірно | 25–45% |
| Дуже малоймовірно | 5–25% |
| Майже виключено | < 5% |

> **Промпт для Claude:** *«У цьому тексті знайди всі судження та оціни, до якого рівня впевненості (висока/помірна/низька) вони відносяться. Якщо рівень не вказаний явно — запропонуй формулювання.»*

### Методологія та оцінка джерел

Секція «Методологія» — частина звіту, яку аналітики найчастіше пропускають. Це помилка.

**Навіщо документувати методологію:**
- Читач розуміє, звідки взялись висновки і наскільки їм довіряти
- Забезпечує відтворюваність — інший аналітик може повторити аналіз
- Юридична захищеність: суд або замовник можуть перевірити ланцюжок доказів
- Виявляє власні прогалини: «я не перевірив X» стає явним

**Що включати в секцію методології:**
```
Інструменти: [перелік із поясненням, як використовувався кожен]
Джерела: [типи джерел, часовий діапазон збору]
Процес верифікації: [як підтверджувалась інформація]
Обмеження: [що НЕ могло бути досліджено і чому]
```

**Правило мінімум трьох джерел:**
Ключовий факт вважається встановленим лише якщо підтверджений **трьома незалежними джерелами**. Незалежними = не посилаються одне на одного, різного типу (первинне + вторинне + верифікуюче).

**Оцінка джерел — матриця надійності:**

| | Первинне | Вторинне | Непідтверджено |
|--|----------|---------|----------------|
| **Перевірене** | ✅ Висока впевненість | ⚠️ Помірна | ❓ Низька |
| **Непідтверджена ідентичність** | ⚠️ Помірна | ❓ Низька | ❌ Не використовувати |

**Цитування — стандарти для OSINT:**
- Завжди вказуйте **дату доступу** (онлайн-контент змінюється і видаляється)
- Зберігайте **архівну копію** (archive.org, локальний скріншот із timestamp)
- Для кожного твердження — посилання на конкретне джерело, а не загальний сайт
- AI-generated контент **не є джерелом**; це інструмент синтезу вже наявних джерел

> **Промпт для документування методології:** *«На основі цього переліку інструментів і дій напиши секцію "Методологія" для OSINT-звіту: що використовувалось, як верифікувалась інформація, які обмеження дослідження.»*

### Що і як делегувати AI у написанні звіту

**Делегувати AI (безпечно):**

| Задача | Промпт |
|--------|--------|
| Чернетка за нотатками | *«На основі цих нотаток напиши чернетку spot report у форматі BLUF + Key Judgements»* |
| Переклад з інших мов | *«Переклади цей текст українською, збережи технічну термінологію»* |
| Нормалізація мови | *«Перепиши цей абзац у нейтральному аналітичному стилі без емоційних оцінок»* |
| Список альтернатив | *«Перелічи 5 альтернативних пояснень для цього патерну поведінки»* |
| Виявлення прогалин | *«Які питання залишаються без відповіді після цього аналізу?»* |
| Резюме для керівника | *«Напиши executive summary у 3 реченнях для нетехнічної аудиторії»* |

**Не делегувати AI (завжди аналітику):**
- Фінальна атрибуція — «хто це зробив»
- Оцінка надійності джерела (знаєш лише ти)
- Ключові судження з юридичними або оперативними наслідками
- Підпис і відповідальність за продукт

**Практичний патерн:**
```
1. Аналітик збирає факти і нотатки (raw intelligence)
2. AI структурує → чернетка звіту
3. Аналітик редагує: додає атрибуції, виправляє судження
4. AI полірує: стиль, граматика, послідовність
5. Аналітик: фінальна перевірка та підпис
```

## Частина ІІ — Prompt Engineering для аналітика

Вміння писати промпти — це не «маніпуляція ChatGPT». Це структурна навичка, аналогічна вмінню формулювати технічне завдання. Погано сформульований промпт → погана відповідь, незалежно від якості моделі.

### Архітектура ефективного промпту

**Промпт для аналітичної роботи — це не запитання.** Це технічне завдання з чітко визначеними параметрами.

**Анатомія сильного аналітичного промпту:**

```
[РОЛЬ]          Ти — досвідчений OSINT-аналітик зі спеціалізацією в...
[КОНТЕКСТ]      Ми розслідуємо... Наразі встановлено, що...
[ЗАВДАННЯ]      Твоє завдання — ...
[ФОРМАТ]        Відповідь у форматі: 1) ... 2) ... 3) ...
[ОБМЕЖЕННЯ]     Не роби припущень без доказів. Якщо даних недостатньо — скажи явно.
[ВХІДНІ ДАНІ]   <текст/дані для аналізу>
```

**Чому кожен елемент важливий:**
- Без ролі → LLM відповідає як загальний помічник, а не аналітик
- Без контексту → втрачає специфіку розслідування
- Без формату → відповідь непридатна для звіту
- Без обмежень → LLM галюцинує «зручні» відповіді

**Слабкий промпт:** *«Проаналізуй цей Telegram-канал»*

**Сильний промпт:**
> *«Ти — OSINT-аналітик, що спеціалізується на виявленні операцій впливу. Нижче — 50 повідомлень з Telegram-каналу за останній тиждень. Встанови: 1) домінуючий наратив; 2) ознаки координованого поширення (синхронізація, ідентичний контент); 3) цільова аудиторія за мовою та темами. Для кожного висновку вкажи рівень впевненості і наведи конкретний приклад з тексту. Де даних недостатньо — скажи явно.»*

### Фреймворк R.O.C.E.

**R.O.C.E.** — структурований підхід до промптів для розвідувальних задач.

```
R — Role        (Роль)
O — Objective   (Ціль)
C — Context     (Контекст)
E — Evidence    (Докази/дані)
```

**Приклад застосування для аналізу персони:**

```
R: Ти — досвідчений аналітик відкритих джерел зі знанням
   цифрових слідів і атрибуції акаунтів.

O: Проведи аналіз цифрового сліду підозрюваного акаунту
   і визнач ймовірне місце базування оператора.

C: Акаунт @example_ua існує з 2019 року, активний переважно
   о 9–18:00 UTC+2. Публікує проросійський контент,
   іноді помиляється між українською і російською в одному повідомленні.
   Відомо, що акаунт раніше був пов'язаний з іншим (@old_handle).

E: [вставити останні 30 повідомлень у форматі timestamp + текст]

Завдання: Встанови мову оригіналу, ймовірний часовий пояс,
тематичні патерни, зв'язок між @example_ua і @old_handle.
Висновки з рівнем впевненості.
```

**Чому R.O.C.E. кращий за вільний промпт:**
- Role активує правильну «режимну модель» в LLM
- Context усуває двозначності без зайвих пояснень
- Evidence структурує вхідні дані → LLM не придумує факти
- Objective виключає відповіді не по темі

### Промпти для конкретних аналітичних задач

**Синтез із кількох джерел:**
```
Нижче — 5 статей про [тему] з різних джерел і дат.
Синтезуй їх у єдиний аналіз:
```

### Analysis of Competing Hypotheses (ACH) з AI

**ACH** — структурована аналітична техніка для боротьби з confirmation bias. Розроблена в ЦРУ Річардсом Хьором.

**Принцип:** Ми не шукаємо докази на підтримку гіпотези — ми **відкидаємо** гіпотези через суперечливі докази.

**ACH матриця:**

| Докази | H1: Координована операція | H2: Органічний рух | H3: Комерційний накрут |
|--------|--------------------------|-------------------|----------------------|
| Синхронізація ±5 хв | ++ | − − | + |
| 78–91% overlap учасників | ++ | − | ++ |
| Ідентичний текст дослівно | ++ | − − | − |
| Різноманітні IP-адреси авторів | − | + | − |
| Монетизації немає | + | ++ | − − |

Позначки: `++` підтримує, `+` слабко підтримує, `−` суперечить, `−−` сильно суперечить, `?` невідомо.

**Висновок:** H1 має найменше суперечностей → найімовірніша.

**Промпт для Claude — побудова ACH матриці:**
```
Побудуй ACH матрицю для наступної ситуації.
Сформулюй 3–5 конкуруючих гіпотез, що пояснюють [явище].
Для кожного доказу зі списку нижче постав оцінку:
++ (сильно підтримує), + (підтримує), ? (нейтрально), - (суперечить), -- (сильно суперечить).
Виведи у вигляді таблиці Markdown.
В кінці: яка гіпотеза має найменшу кількість суперечностей?

Докази: [список фактів]
```

```python

from jinja2 import Environment, FileSystemLoader
import json

# 1. Завантаження і агрегація
df = pd.read_csv("telegram_events.csv", parse_dates=["timestamp"])
df["date"] = df["timestamp"].dt.date

daily = df.groupby("date").agg(
    messages=("message_id", "count"),
    unique_channels=("channel_id", "nunique")
).reset_index()

# 2. Автоматичний графік
fig = px.line(daily, x="date", y="messages",
              title="Активність мережі каналів по днях",
              labels={"messages": "Кількість повідомлень", "date": "Дата"})
fig.write_image("activity_chart.png", width=1200, height=500)

# 3. Ключові метрики для звіту
stats = {
    "total_messages": int(df.shape[0]),
    "total_channels": int(df["channel_id"].nunique()),
    "peak_day": str(daily.loc[daily["messages"].idxmax(), "date"]),
    "peak_count": int(daily["messages"].max()),
    "date_from": str(df["timestamp"].min().date()),
    "date_to": str(df["timestamp"].max().date()),
}

# 4. Генерація звіту через Jinja2
env = Environment(loader=FileSystemLoader("."))
template = env.get_template("report_template.md")
report = template.render(**stats)

with open("report_output.md", "w", encoding="utf-8") as f:
    f.write(report)
```

## Частина ІVб — Геопросторові візуалізації в звіті

Карта в звіті — це не ілюстрація. Це доказовий матеріал із власними вимогами до оформлення. Ця частина про те, коли карта підсилює звіт, а коли лише додає шум, і як обрати правильний інструмент.

### Карта в OSINT-звіті: коли і як

**Коли карта додає цінності:**
- Подія або об'єкт прив'язані до конкретної локації (геолокована фотографія, маршрут техніки)
- Потрібно показати просторовий патерн (кластеризація публікацій за регіонами)
- Верифікація: «де заявлено» vs «де це фізично»
- Рух або маршрут є частиною знахідки

**Коли карта зайва:**
- «Маємо дані з Telegram — покажемо на карті України» без просторового змісту
- Якщо точність геолокації <30 км — крапка на карті вводить в оману
- Якщо карта лише дублює таблицю з координатами без додаткового сенсу

**Стандарти публікаційної карти (обов'язково для звіту):**

| Елемент | Навіщо |
|---------|--------|
| Масштабна лінійка + Північ | Читач розуміє відстані та орієнтацію |
| Легенда для кожного шару | Символ без пояснення — не доказ |
| Джерело підложки + дата знімку | Відтворюваність; знімки змінюються |
| Координатна сітка або bbox | Дозволяє незалежно перевірити локацію |
| CRS / проєкція | Обов'язково якщо є вимірювання відстаней |

**Промпт для AI — описати просторову знахідку словами:**
```
Я маю координати 12 подій з атрибутами [тип, дата, джерело].
Опиши просторовий патерн для секції Findings звіту:
чи є кластеризація, яка відстань між групами, який регіон охоплюють?
Не роби оцінювальних суджень — лише опис просторових характеристик.
```

### QGIS: від даних до звітної карти

**QGIS** — безкоштовна крос-платформна GIS із відкритим кодом. **Print Layout** — саме та функція, що дає публікаційний результат із масштабною лінійкою, легендою і підписом джерела.

**Звітний pipeline в QGIS:**
```
CSV / GeoJSON (lat, lon + атрибути)
        ↓  Layer → Add Delimited Text Layer
Точковий шар на полотні
        ↓  QuickMapServices → Google Satellite Hybrid
Аналітика (за потребою)
        ↓  Processing → Heatmap / Buffer / Spatial Join
Стилізація
        ↓  Layer Properties → Symbology → колір/розмір за атрибутом
Print Layout
        ↓  Project → New Print Layout
Експорт
        ↓  Export as Image (PNG 300 dpi) або Export as PDF
```

**Print Layout — обов'язкові елементи:**
- `Add Item → Map` — вставити вид карти в макет
- `Add Item → Scale Bar` — масштабна лінійка
- `Add Item → North Arrow` — Північ
- `Add Item → Legend` — авто-легенда зі стилів шарів
- `Add Item → Label` — підпис: джерело підложки, CRS, дата

**Ключові QGIS-плагіни для OSINT-репортингу:**
- **QuickMapServices** — супутникові підложки Google/Bing/ESRI одним кліком
- **QuickOSM** — витягти інфраструктуру OSM за тегами прямо в QGIS (`amenity=hospital`, `military=base` тощо)
- **Streetview** — перехід до Google Street View для геолокаційної верифікації

**Підготовка даних у Python перед QGIS:**
```python
df_map = df[["lat", "lon", "event_type", "date", "source"]].dropna(subset=["lat", "lon"])
df_map.to_csv("events_for_map.csv", index=False, encoding="utf-8")
# Обов'язково: окремі поля lat і lon у десятковому форматі (50.4501, а не 50°27'N)
```

### Альтернативи QGIS: вибір інструменту під задачу

| Інструмент | Сильна сторона | Обмеження | Коли обирати |
|------------|---------------|-----------|-------------|
| **QGIS** | Повний GIS-аналіз, OSM-запити, PDF-друк | Крива навчання | Просторовий аналіз, звіт для друку |
| **Kepler.gl** | Мільйони точок, Trip-анімація, HTML-звіт | Немає spatial join, тільки браузер | Великий датасет, веб-публікація |
| **Google Earth Pro** | Historical Imagery, KMZ/KML overlay, безкоштовно | Закритий, не аналітичний | Швидка геолокаційна верифікація |
| **Felt** (felt.com) | Сучасний колаборативний веб-редактор | Хмарний — не для чутливих кейсів | Командна робота, швидка публікація |
| **uMap** (umap.openstreetmap.fr) | Open source, self-hostable | Обмежені шари, нема аналітики | Публічні мапи, self-hosted для чутливих |
| **Datawrapper** | Хороплет-карти для публікацій за 5 хв | Лише агреговані дані, без точок | Choropleth по країнах/регіонах |

**Правило вибору:**
- Чутливий кейс → **QGIS** (локально) або **self-hosted uMap**
- Багато точок → **Kepler.gl**
- Порівняння зі супутниковим знімком → **Google Earth Pro**
- Карта для публічного звіту або медіа → **Datawrapper** або **Felt**
- Просторовий аналіз (buffer, join, overlay) → тільки **QGIS**

**Kepler.gl у Python — карта прямо зі звіту:**
```python
from keplergl import KeplerGl

map_1 = KeplerGl(height=600)
map_1.add_data(data=df_map, name="events")
map_1.save_to_html(file_name="report_map.html")
# → самодостатній HTML-файл, вбудовується в будь-який веб-звіт
```

## Частина V — Агентні воркфлоу

AI найпотужніший не як «відповідальник на одне запитання», а як агент, що самостійно розбиває задачу на кроки, викликає інструменти і адаптує план при несподіваних результатах.

### Від одного промпту до мульти-кроку

**Одноразовий промпт** — один запит → одна відповідь. Підходить для простих задач.

**Агентний воркфлоу** — LLM самостійно розбиває задачу на кроки, викликає інструменти, оцінює результати і продовжує до виконання мети.

**ReAct паттерн (Reason + Act):**
```
Ціль: «Знайди всю публічно доступну інформацію про домен malicious-site.com»

Крок 1:
  THINK: Спочатку перевірю WHOIS для реєстрації і власника
  ACT:   whois_lookup("malicious-site.com")
  OBS:   Реєстратор: Namecheap, дата: 2025-11-03, email: admin@fastmail.com

Крок 2:
  THINK: Email admin@fastmail.com — перевірю витоки баз
  ACT:   haveibeenpwned_check("admin@fastmail.com")
  OBS:   Знайдено в 2 витоках (LinkedIn 2021, Canva 2019)

Крок 3:
  THINK: Перевірю пасивний DNS для пов'язаних доменів
  ACT:   passive_dns("malicious-site.com")
  OBS:   IP 185.220.101.x — також хостить evil-news.net, fake-media.org

Крок 4:
  THINK: Достатньо для spot report. Формую висновки.
  ACT:   generate_report(findings)
```

**Інструменти, які Claude Code може викликати:**
- `WebSearch` → пошук у відкритих джерелах
- `Bash` → запуск Python скриптів, curl, whois
- `Read/Write` → читання і запис файлів
- MCP-сервери → Gephi, ArkhamMirror, Neo4j, зовнішні API

### Claude як OSINT-агент: практичний приклад

**Задача:** Зібрати цифровий профіль домену і скласти короткий технічний бриф.

**Промпт:**
```
Проведи OSINT-аналіз домену [target.example.com].
Використовуй доступні інструменти послідовно:
1. WHOIS (реєстрація, власник, дата)
2. DNS записи (A, MX, TXT, NS)
3. Пошук у відкритих джерелах (новини, форуми)
4. SSL-сертифікат (CN, організація, дата)

Після кожного кроку — коротко зафіксуй знахідки.
Фінальний звіт: BLUF + ключові факти + рівень загрози (low/medium/high) з обґрунтуванням.
Де даних недостатньо — скажи явно.
```

**Що відбувається всередині:**
```python
bash("whois target.example.com")
bash("dig target.example.com ANY +short")
web_search("target.example.com site:pastebin.com OR site:github.com")
bash("openssl s_client -connect target.example.com:443 </dev/null 2>/dev/null | openssl x509 -noout -text")
# → Синтезує результати → Пише звіт у Markdown
write("domain_brief.md", report_content)
```

**Переваги агентного підходу:**
- Аналітик описує **ціль**, а не **кроки**
- Агент адаптує план при неочікуваних результатах
- Кожен крок задокументований (трейс)
- Повторюваний: однаковий промпт = однакова методологія для всіх кейсів

### Повний OSINT-воркфлоу з AI: кейс

**Сценарій:** Розслідування координованої дезінформаційної кампанії. Від отримання задачі до готового звіту — 4 години замість 2 днів.

```
КРОК 1 — Збір [30 хв]
  Groupint → 47 Telegram-каналів → Neo4j
  Claude (агент): автоматичний WHOIS всіх доменів зі статей

КРОК 2 — Мережевий аналіз [20 хв]
  gephi-ai + Claude → modularity, betweenness, PageRank
  → автоматичний граф PNG + GEXF

КРОК 3 — Контент-аналіз [25 хв]
  Python скрипт (Claude-generated) → cosine similarity матриця
  → 11 каналів з ідентичним контентом ±3 хв → CSV

КРОК 4 — Синтез [15 хв]
  Промпт Claude (R.O.C.E.): синтез знахідок з кроків 2–3
  → ACH матриця: 3 гіпотези → H1 (координована операція) найімовірніша

КРОК 5 — Звіт [30 хв]
  Jinja2 шаблон + pandas stats → автоматична чернетка Markdown
  Claude: відполірувати стиль, перевірити рівні впевненості
  Аналітик: додати атрибуцію, підпис, фінальна вичитка
  → PDF звіт

ЗАГАЛЬНИЙ ЧАС: ~2 год (ручна робота аналітика: ~45 хв)
БЕЗ AI: 2–3 робочі дні
```

### Де AI помиляється в аналітичній роботі

Знати обмеження AI — так само важливо, як знати його можливості.

**1. Галюцинації фактів**
LLM може «вигадати» цитату, дату, ім'я або URL, якого не існує. Правило: **ніколи не включати факт у звіт, якщо він не верифікований незалежним джерелом.** Промпт-обережність: *«Якщо ти не впевнений у факті — скажи 'невідомо', не вигадуй»*

**2. Підтвердження упередженості через формулювання**
Якщо запитати *«Доведи, що це координована операція»* — LLM знайде докази. Якщо запитати *«Які аргументи проти гіпотези про координацію?»* — знайде інші. Рішення: завжди запитувати обидві сторони, використовувати ACH.

**3. Переоцінка форми**
Гладко написаний абзац від LLM звучить переконливо — незалежно від якості доказів. Форма не є доказом змісту.

**4. Витік чутливих даних**
Не вставляти у комерційні LLM API дані, що ідентифікують суб'єктів розслідування (PII). Для чутливих кейсів → локальні моделі (Ollama + Gemma/Llama).

**5. Залежність від AI**
Аналітик, що перестає перевіряти AI-висновки, перестає бути аналітиком.

### Ключові принципи: підсумок уроку

**Стандарти звіту:**
- BLUF: ключовий висновок — першою фразою, завжди
- Рівні впевненості: висока / помірна / низька — явно для кожного судження
- ACH: відкидати гіпотези через суперечності, не підтверджувати через збіги

**Prompt Engineering:**
- Фреймворк R.O.C.E.: роль + ціль + контекст + докази
- Конкретні задачі = конкретні промпти (не «проаналізуй», а «знайди X у форматі Y»)
- Ітеративний рефайнинг — нормально і ефективно

**Автоматизація та візуалізація:**
- Obsidian + Dataview → живий дашборд розслідування
- Python + Jinja2 → автоматичні звіти зі стандартного шаблону
- Plotly → аналітичні часові та мережеві візуалізації
- QGIS Print Layout → публікаційна карта з легендою і масштабом
- Kepler.gl / Datawrapper → карти для веб-звітів і великих датасетів

**Агентний воркфлоу:**
- Агентний Claude Code → багатокрокові OSINT-задачі
- ReAct: THINK → ACT → OBSERVE; кожен крок задокументований

> **Золоте правило:** AI прискорює процес — аналітик несе відповідальність за висновки. Підпис під звітом завжди людський.
