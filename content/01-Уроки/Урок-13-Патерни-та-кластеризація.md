### Слайд 7 — ЯК ПОБУДОВАНО BITCOINTEMPORALGRAPH

- 1. Сирі дані
- Вузол Bitcoin Core → файли blk*.dat; перші 700 000 блоків, ~13 років історії
- 2. Скрипти
- Кожен вихід (TXO) захищений locking script; нульові TXO відкинуто → понад 874 млн скриптів
- 3. Кластери
- Евристики об’єднують скрипти одного власника → ~252 млн сутностей, це і є вузли
- 4. Ребра
- Чиста сума v(a) = отримано − витрачено: v > 0 — отримувач, v < 0 — відправник
- 5. Фільтри
- CoinJoin (JoinMarket, Wasabi, Whirlpool) і colored coins (Omni, Open Assets, EPOBC) виключено
- 6. Атрибути
- Ребро: reveal, last_seen, total, min/max/total_sent. Вузол: ступені, суми, часові межі, розмір кластера

### Слайд 8 — ФОРМУЛА РЕБРА НА ПРИКЛАДІ

Приклад транзакції з рештою (схема на слайді): входи A = 1,0 BTC, B = 0,5 BTC; вихід C = 1,2 BTC; решта на A = 0,29 BTC; комісія майнеру 0,01 BTC.

- `v(a) = Σ виходів a − Σ входів a`
- `v(A) = 0,29 − 1,0 = −0,71` → відправник
- `v(B) = 0 − 0,5 = −0,5` → відправник
- `v(C) = 1,2 − 0 = +1,2` → отримувач
- Частки входів: A = 1,0 / 1,5 = ⅔, B = ⅓
- Ребра: A → C = ⅔ × 1,2 = 0,8 BTC; B → C = ⅓ × 1,2 = 0,4 BTC
- Решта A → A не створює ребра
- Модельне рішення: розподіл за часткою входів — фіксуйте це в методології.

### Слайд 9 — OSINT-РОЗМІТКА: BITCOINTALK + LLM

**BitcoinTalk:** 14 067 713 постів, 546 440 тем (англ.); контекст = тема, пост, деталі tx + курс USD на дату.

**gpt-4o-mini:** 4 типи промптів (депозит, виведення, hot/cold) → міркування, назва сутності, тип, адреси.

**Мітка вузла:** назва → категорія; конфлікт → без мітки.

- Депозит: скарга, що кошти не зараховано → адреса депозиту належить сервісу
- Виведення: сервіс повідомив txid → входи tx = гарячий гаманець сервісу
- Виведення без txid: пошук tx ±3 дні на адресу з сумою; якщо одна — атрибуція
- Назву сутності мапують на 11 категорій; адреса → скрипти → кластер (вузол)
- Кілька різних міток в одному кластері → мітку не ставлять
- Це класичний OSINT: офчейн-контекст дає атрибуцію ончейн-адрес.

### Слайд 15 — ЧОМУ ГРАФОВА БАЗА ДАНИХ

**SQL (PostgreSQL):** рекурсивний CTE для 3 хопів — довгий і важкий для підтримки.

**Cypher (Neo4j):** той самий запит компактніше:

```cypher
MATCH (:Wallet {address: '1Abc...'})-[:SENT_TO*1..3]->(w:Wallet)
RETURN DISTINCT w.address;
```

- PostgreSQL (як у статті): масове сховище на 120 ГБ, вибірки, агрегати
- Neo4j: багатокрокові шляхи, патерни, алгоритми GDS, швидка візуальна перевірка
- Практичне правило: велике сховище — у SQL, підграф розслідування — у Neo4j.

### Слайд 17 — МОДЕЛЬ ДАНИХ У NEO4J

Три графи в одному датасеті:

| Елемент | Зміст |
| --- | --- |
| `(:Transaction)` | `txId`, `timeStep`, `class`, `nIn`, `nOut`, `totalBTC`, `fees`, `outMin`, `outMax` |
| `(:Wallet)` | `address`, `class`, `firstStep`, `lastStep` |
| `[:FLOWS_TO]` | tx → tx (потік коштів) |
| `[:INPUT]` / `[:OUTPUT]` | wallet ↔ tx (двочастковий) |
| `[:SENT_TO {n}]` | wallet → wallet; `n` — скільки разів пара зустрілась |

Один датасет — три графи: потік коштів (tx → tx), взаємодія гаманців (addr → addr), двочастковий (addr → tx → addr).

### Слайд 19 — ІМПОРТ: LOAD CSV

Обмеження унікальності — **до** імпорту. Повний скрипт — `01_import.cypher`.

```cypher
CREATE CONSTRAINT tx_id IF NOT EXISTS
FOR (t:Transaction) REQUIRE t.txId IS UNIQUE;
CREATE CONSTRAINT wallet_addr IF NOT EXISTS
FOR (w:Wallet) REQUIRE w.address IS UNIQUE;

LOAD CSV WITH HEADERS FROM 'file:///tx_nodes.csv' AS row
CALL (row) {
  CREATE (:Transaction {txId: toInteger(row.txId), ...})
} IN TRANSACTIONS OF 10000 ROWS;

LOAD CSV WITH HEADERS FROM 'file:///sent_to.csv' AS row
CALL (row) {
  MATCH (a:Wallet {address: row.input_address})
  MATCH (b:Wallet {address: row.output_address})
  CREATE (a)-[:SENT_TO {n: toInteger(row.n)}]->(b)
} IN TRANSACTIONS OF 20000 ROWS;
```

Імпорт: 4 хв 17 с на 2 CPU / 7 ГБ RAM; найдовше — `SENT_TO` (147 с).

### Слайд 22 — CYPHER: КОНСОЛІДАЦІЯ ТА ЕКСПОЗИЦІЯ

- Fan-in: хто збирає кошти
```cypher
MATCH (s:Wallet)-[:SENT_TO]->(w:Wallet)
WITH w, count(s) AS senders
WHERE senders >= 100
RETURN w.address, w.class, senders
ORDER BY senders DESC LIMIT 10;
```
- Експозиція: куди доходять кошти illicit
```cypher
MATCH (i:Wallet {class: 1})
-[:SENT_TO*1..2]->(u:Wallet {class: 3})
WITH u, count(DISTINCT i) AS exposure
WHERE exposure >= 5
RETURN u.address, exposure
ORDER BY exposure DESC LIMIT 10;
```
- Результат на Elliptic++ (4,3 с): ≥ 100 відправників мають 2 680 гаманців — 2 078 licit, 578 unknown, лише 24 illicit
- Топ-1: 11 213 відправників, licit. Fan-in — передусім сервіси, а не злочин
- Результат (0,5 с): два unknown-гаманці отримують кошти від 1 061 illicit-гаманця кожен, далі — 319 і 190
- Однакові значення — підказка, що це адреси одного сервісу: перевірте fan-in і офчейн

### Слайд 23 — CYPHER: PEEL CHAIN, ЦИКЛИ, ШЛЯХИ

```cypher
// Peel chain: >= 5 tx поспіль з 2 виходами, «відщеп» < 10% від більшого виходу
MATCH p = (s:Transaction {class: 1})-[:FLOWS_TO*5..8]->(:Transaction)
WHERE all(t IN nodes(p) WHERE t.nOut = 2 AND t.outMin < 0.1 * t.outMax)
RETURN length(p) AS hops, [t IN nodes(p) | t.txId] AS chain LIMIT 5;
// Цикли: повернення за 2–4 кроки
MATCH p = (w:Wallet {class: 1})
-[:SENT_TO*2..4]->(w)
RETURN [x IN nodes(p) | x.address] LIMIT 5;
// Найкоротший шлях між двома гаманцями
MATCH (a:Wallet {address: $from})
MATCH (b:Wallet {address: $to})
MATCH p = shortestPath((a)-[:SENT_TO*..8]->(b))
RETURN [x IN nodes(p) | x.address], length(p);
```
- Peel chain (0,14 с): умову «2 виходи, малий < 10%» задовольняють 102 777 tx — половина датасету; ланцюг ≥ 5 стартує з 366 illicit-tx, найдовший — 182 кроки. Поріг надто загальний
- Цикли (1,8 с): приклад проходить через хаб-гаманець з 11 213 відправниками (licit) — round-trip через сервіс, а не обов’язково «відмивання»
- Шлях: від illicit-гаманця до головного отримувача illicit-коштів — 2 кроки через інший illicit-гаманець

### Слайд 24 — GRAPH DATA SCIENCE: ЦИКЛ РОБОТИ

- 1. Проєкція
- 2. Оцінка пам’яті
- 3. Алгоритм
- 4. Аналіз у Cypher
- 5. Експорт у Gephi
- // 1. Граф у пам'яті: гаманці, неорієнтовано, вага n
- CALL gds.graph.project('wallets', 'Wallet',
- {SENT_TO: {orientation: 'UNDIRECTED', properties: 'n'}});
- // 2. Скільки пам'яті потрібно?
- CALL gds.louvain.write.estimate('wallets',
- {writeProperty: 'louvain'}) YIELD requiredMemory;
- // 3. Алгоритм -> властивість у базі
- CALL gds.louvain.write('wallets', {writeProperty: 'louvain',
- relationshipWeightProperty: 'n'})
- YIELD communityCount, modularity;

**Режими виконання**

- stream — подивитися результат
- stats — лише підсумок
- mutate — у проєкцію, для наступного алгоритму
- write — записати у вузли бази
- Проєкція живе в пам’яті: після роботи — CALL gds.graph.drop('wallets').

### Слайд 28 — ТРИ ЗНАЧЕННЯ «КЛАСТЕРИЗАЦІЇ»

- **1** — Кластери адрес
- Entity resolution
- Питання: які адреси належать одному власнику?
- Метод: евристики спільних входів і решти
- Результат: вузол = сутність (як у BitcoinTemporalGraph)
- **2** — Спільноти в графі
- Community detection
- Питання: хто взаємодіє щільніше, ніж з рештою?
- Метод: WCC, Louvain, Leiden
- Результат: групи гаманців або сутностей
- **3** — Кластери ознак
- Feature clustering
- Питання: хто поводиться схоже?
- Метод: k-means на ознаках або ембедингах (FastRP)
- Результат: поведінкові профілі
- Пишіть у звіті, яку саме кластеризацію застосовано: це три різні твердження.

### Слайд 29 — ЕВРИСТИКИ КЛАСТЕРИЗАЦІЇ АДРЕС

_На слайді схема tx з адресами A–E: синій = одна оцінена сутність (A, B, C — спільні входи; E — імовірна решта)._

- **Спільні входи (common-input ownership):** усі входи однієї tx підписує один власник → адреси об’єднуються
- **Адреса решти (change):** новий вихід того ж типу, «некругла» сума, адреса з’являється вперше
- У статті: евристики з arXiv 2403.00523 — 874 млн скриптів → ~252 млн кластерів
- Хибне злиття незворотне: один CoinJoin, пропущений фільтром, «склеює» сторонніх людей в одну сутність.

### Слайд 30 — COINJOIN: ЧОМУ ЙОГО ВИКЛЮЧАЮТЬ

- CoinJoin
- Кольори входів — різні власники; 4 виходи по 0,1 BTC — нерозрізненні

**Що відбувається**

- Кілька користувачів в одній транзакції
- Рівні виходи ховають, хто кому заплатив
- Евристика спільних входів дає хибне злиття

**Що зробили автори**

- Детекція евристиками для JoinMarket, Wasabi, Whirlpool (arXiv 2311.12491)
- Виключено і з кластеризації, і з ребер графа
- CoinJoin — сигнал бажання приватності, а не доказ злочину.

### Слайд 31 — СПІЛЬНОТИ: LOUVAIN І LEIDEN

**Модулярність Q**

- Частка ребер усередині спільнот мінус очікувана при випадкових зв’язках

**Louvain (Blondel et al., 2008)**

- Жадібно переносить вузли між спільнотами й «згортає» граф рівнями

**Leiden (Traag et al., 2019)**

- Додає крок уточнення: спільноти гарантовано зв’язні

**Resolution γ**

- Більше γ → більше дрібних спільнот
- CALL gds.louvain.write('wallets', {
- writeProperty: 'louvain',
- relationshipWeightProperty: 'n'})
- YIELD communityCount, modularity;
- CALL gds.leiden.write('wallets', {
- writeProperty: 'leiden',
- relationshipWeightProperty: 'n',
- gamma: 1.0})
- YIELD communityCount, modularity;
- Біржі й великі сервіси — «супервузли»: вони склеюють спільноти. Позначте або виключіть їх перед запуском.
