## Приклад 1: WEBINT-розслідування (Module W1)

**Сценарій:** Ви отримали завдання зібрати OSINT на компанію, яка підозрюється у схемах ухилення від санкцій.

### Команда запуску:

```
Activate module: web_search_osint
Input:
{
  "search_parameters": {
    "target_entity": "Meridian Trading Group",
    "entity_type": "company",
    "intelligence_requirement": "санкційна відповідність, кінцеві бенефіціари, транзакційні паттерни"
  },
  "source_prioritization": {
    "high": ["корпоративні реєстри", "судові документи", "OFAC SDN list"],
    "medium": ["LinkedIn", "новинні архіви"],
    "low": ["соцмережі"]
  },
  "temporal_constraints": {
    "start": "2022-01-01",
    "end": "2025-12-31"
  }
}
```

### Очікуваний формат відповіді:

```
//DISCLAIMER: Цей процес збору WEBINT обмежений публічно доступними джерелами.
Верифікація через первинні джерела обов'язкова перед операційним використанням.

//RESULT: Search Methodology
- Корпоративний реєстр: пошук варіантів назви + пов'язаних юрисдикцій
- OFAC SDN crosscheck: прямий та непрямий зв'язок
- LinkedIn corporate graph: ключові особи → мережа зв'язків
- News archive: 2022-2025, фільтр по "sanctions" + "trading"

//RESULT: Collected Intelligence
[Entity Graph]
- Meridian Trading Group → зареєстрована: Дубай (ОАЕ), 2021
- Директор: [ім'я] — попередня компанія: [X Corp, Moscow 2019]
- Банк-кореспондент: Bank of [Country], відзначений у звіті FinCEN 2023

//ANOMALY: Невідповідність у датах реєстрації (офіційна: 2021, LinkedIn-профіль директора вказує 2020)

//QUERY: Потрібна верифікація через UAE company registry. Чи є доступ?
```

### Що показує цей приклад:
- `//DISCLAIMER` завжди з'являється першим — система нагадує про обмеження
- `//ANOMALY` автоматично виділяє невідповідності (не треба просити)
- `//QUERY` запитує тільки те, що реально потрібно для продовження

## Приклад 2: Стратегічний аналіз (Module S1)

**Сценарій:** Підготовка аналітичного продукту про можливі сценарії розвитку регіонального конфлікту.

### Команда запуску:

```
Activate module: strategic_scenario_modeling
Input:
{
  "geopolitical_context": "Країна A ввела нові торговельні обмеження проти країни B.
    Б реагує посиленням військової присутності на спільному кордоні.
    Третя сторона C має енергетичну залежність від обох.",
  "time_horizon": "medium-term (6-18 місяців)",
  "variables_of_interest": [
    "ескалація військової присутності",
    "рішення країни C",
    "позиція міжнародних організацій"
  ],
  "historical_precedents": [
    "Торговельна війна США-Китай 2018-2019",
    "Газова криза ЄС 2022"
  ]
}
```

### Очікуваний формат відповіді:

```
//RESULT: Key Factors
1. Економічний важіль країни A (торговельні обмеження) — висока значущість
2. Військова сигналізація країни B — середня значущість (поки що сигнал, не дія)
3. Енергетична вразливість C — критична змінна (визначає вибір сторони)

//RESULT: Baseline Scenario (ймовірність ~55%)
Переговорний тупик + часткова деескалація через 4-6 міс.
Тригери: C обирає нейтралітет, A пом'якшує умови для збереження обличчя
Індикатори моніторингу: дипломатичні зустрічі рівня міністрів, енергетичні контракти C

//RESULT: Alternative Scenario 1 (ймовірність ~25%)
Ескалація: B здійснює обмежені прикордонні дії
Тригери: C відкрито приєднується до A, B відчуває оточення
Попереджувальні індикатори: масова мобілізація, закриття повітряного простору

//RESULT: Alternative Scenario 2 (ймовірність ~20%)
Регіональна деескалація через посередника
Тригери: Енергетична криза змушує всі сторони до переговорів
Умови: зовнішній медіатор (D або міжнародна організація)

//AMATERASU: Сценарій 1 потребує щотижневого моніторингу [5 ключових індикаторів].
Рекомендую активувати модуль S4 для трендового аналізу.
```

### Що показує цей приклад:
- Ймовірності explicit і відкалібровані (не "можливо" / "вірогідно")
- `//AMATERASU` сам пропонує наступний крок аналізу
- Тригерні індикатори — actionable: аналітик знає, що моніторити

## Приклад 3: Сесійний експорт і продовження роботи

**Сценарій:** Ви провели 2-годинний аналіз. Потрібно зберегти і продовжити завтра.

### Збереження сесії:

```
Export session
```

**Вивід (скорочено):**

```json
{
  "session_id": "TSUK-2025-0614-ALPHA",
  "timestamp": "2025-06-14T14:32:00Z",
  "modules_executed": [
    "data_recognition_ingestion",
    "discipline_alignment", 
    "web_search_osint"
  ],
  "intelligence_context": {
    "target": "Meridian Trading Group",
    "key_findings": ["UAE registration 2021", "FinCEN flag 2023"],
    "open_queries": ["UAE registry verification"],
    "confidence_levels": {"entity_identification": 0.82, "sanctions_nexus": 0.61}
  },
  "next_recommended_modules": ["source_correlation_matrix", "actor_capability_assessment"]
}
```

### Відновлення наступного дня:

```
Import session: [вставте JSON вище]
```

**Вивід:**

```
//TSUKUYOMI: Session TSUK-2025-0614-ALPHA restored.
Context loaded: Meridian Trading Group investigation.
Pending query: UAE registry verification.
Recommended next step: source_correlation_matrix
Proceed? [y/n]
```

### Що показує цей приклад:
- Сесія зберігає не просто "що було зроблено", а **рівні впевненості** та **відкриті питання**
- `next_recommended_modules` — система сама планує workflow
- Відновлення повністю seamless — без повторного введення контексту

## Порівняння: з TSUKUYOMI vs без

| | Без фреймворку | З TSUKUYOMI |
|--|---------------|-------------|
| **Формат відповіді** | Вільний текст | Структуровані теги `//` |

| **Аномалії** | Треба помітити самому | `//ANOMALY` автоматично |
