### Слайд 2 — Чому промптинг — це не просто «написати запит»

**Проблема:** 73% аналітиків отримують неповні або неточні відповіді від LLM

**Причина:** Вони спілкуються з LLM як із пошуковиком

**Реальність:**
- LLM — це статистична модель, що передбачає токени
- Якість виводу прямо залежить від якості **контексту**
- Один і той самий запит дає різний результат залежно від структури

**Мета лекції:** Навчитися інженерити контекст так, щоб LLM видавав точний, верифікований, структурований OSINT-продукт

### Слайд 5 — Фреймворк P-R-O-M-P-T

**P** — **Persona** (Роль) → Хто ти? Аналітик CTI? Слідчий?
**R** — **Request** (Запит) → Що конкретно потрібно?
**O** — **Output format** (Формат) → JSON? Таблиця? Markdown?
**M** — **Mission context** (Контекст) → Що ми вже знаємо?
**P** — **Parameters** (Обмеження) → Мова, стиль, джерела
**T** — **Temperature** (Точність vs Творчість) → 0.0–0.2 для OSINT

**Приклад (поганий запит):**
> "Розкажи про компанію XYZ"

**Приклад (P-R-O-M-P-T):**
> "Ти — аналітик due diligence з 10-річним досвідом (P). Витягни з наведеного тексту: назву компанії, юрисдикцію, засновників і ознаки скаму (R). Формат — JSON (O). Контекст: перевіряємо інвестиційну пропозицію (M). Лише факти, без домислів (P)."

### Слайд 9 — Chain of Thought (CoT): принцип

**Що таке CoT:** Змушуємо LLM «думати вголос» крок за кроком перед відповіддю

**Без CoT:**
> Запит: "Чи є цей домен підозрілим?"
> Відповідь: "Так, виглядає підозріло" — ❌ непридатно для OSINT

**З CoT:**
> Запит: "Проаналізуй домен secure-bank-ua[.]com крок за кроком:
> 1. Розбий назву домену на складові
> 2. Визнач що намагається імітувати
> 3. Оціни ознаки фішингу
> 4. Зроби висновок з рівнем впевненості A/B/C/D"

**Результат:** 86% точність (vs 61% без CoT)
*Джерело: Journal of Information Warfare, 2025*

### Слайд 10 — Типи CoT для OSINT (2025-2026)

| Варіант CoT | Опис | Коли використовувати |
|------------|------|---------------------|
| **Standard CoT** | "Думай крок за кроком" | Більшість задач |

**Увага 2025:** Wharton Business School показала — CoT **знижує** якість простих задач. Використовуй CoT лише для складного аналізу.

### Слайд 12 — RAG: LLM + зовнішні джерела

**Проблема LLM без RAG:**
- Знання обрізані датою навчання
- Немає доступу до живих даних
- "Галюцинації" при браку контексту

**RAG (Retrieval-Augmented Generation) вирішує це:**

```
ЗАПИТ АНАЛІТИКА
      │
      ▼
[Векторний пошук] ←── [База знань: документи, звіти, бази IoC]
      │
      ▼
[Релевантні чанки] ──► [LLM] ──► [Відповідь з посиланнями]
```

**OSINT-застосування RAG:**
- Perplexity / Exa AI → пошук у реальному часі
- Obsidian + векторний плагін → ваш OSINT-архів
- Custom RAG → база IoC + звіти + WHOIS-дані

### Слайд 17 — Z-score аномалії: повний пайплайн

```python
import pandas as pd
import numpy as np

# 1. Завантажуємо дані
df = pd.read_csv('osint_accounts.csv')

# 2. Обчислюємо Z-score для активності
df['z_messages'] = (df['messages_per_day'] - df['messages_per_day'].mean()) \
                   / df['messages_per_day'].std()

# 3. Виявляємо аномалії
anomalies = df[df['z_messages'].abs() > 2.5]

# 4. Формуємо промпт для LLM
anomaly_table = anomalies[['username', 'messages_per_day', 
                            'z_messages', 'created_date']].to_markdown()

prompt = f"""
АНОМАЛЬНІ АКАУНТИ (Z-score > 2.5):

{anomaly_table}

Для кожного акаунту визнач:
А) Тип аномалії: бот / координована мережа / реальний активіст
Б) Докази твого висновку
В) Рекомендація: слідкувати / заблокувати / продовжити дослідження

Формат — таблиця Markdown.
"""
```

**Результат:** LLM аналізує тільки реальні аномалії, не всі 500 рядків

### Слайд 20 — Мережевий граф з таблиці

**Кейс:** CSV зі зв'язками → граф → LLM-інтерпретація

```python
import networkx as nx
import pandas as pd

# Завантажуємо зв'язки
edges_df = pd.read_csv('connections.csv')  # source, target, weight, type

# Будуємо граф
G = nx.from_pandas_edgelist(edges_df, 'source', 'target', 
                             edge_attr=['weight', 'type'])

# Обчислюємо метрики
betweenness = nx.betweenness_centrality(G)
top_nodes = sorted(betweenness.items(), 
                   key=lambda x: x[1], reverse=True)[:10]

metrics_md = pd.DataFrame(top_nodes, 
                          columns=['node', 'betweenness']).to_markdown()

prompt = f"""
ТОП-10 ВУЗЛІВ ЗА BETWEENNESS CENTRALITY:

{metrics_md}

ЗАГАЛЬНА СТАТИСТИКА ГРАФУ:
- Вузлів: {G.number_of_nodes()}
- Зв'язків: {G.number_of_edges()}
- Компонент: {nx.number_connected_components(G.to_undirected())}

ІНТЕРПРЕТАЦІЯ:
1. Хто є ключовими посередниками (брокерами інформації)?
2. Вузол з найвищим betweenness — яка його роль у мережі?
3. Чи є "мости" між окремими кластерами?
4. Які вузли найбільш критичні для зв'язності мережі?
```

### Слайд 23 — Промпт для витягу IoC

**Вхідні дані:** Звіт загрози у вільному тексті

```
РОЛЬ: Ти — спеціаліст CTI з сертифікацією GIAC.

ЗАВДАННЯ: Витягни всі Indicators of Compromise (IoC) 
з наведеного звіту.

ФОРМАТ — JSON масив:
{
  "ioc_type": "IP|Domain|Hash|Email|URL|Registry|Mutex",
  "value": "...",
  "context": "що робить цей IoC",
  "mitre_technique": "T1234 або null",
  "confidence": "HIGH|MEDIUM|LOW",
  "defanged": true/false
}

ВАЖЛИВО:
```

### Слайд 26 — Три провали LLM у CTI

**Провал 1: Spurious Correlations (хибні кореляції)**
```
❌ Проблема: LLM знаходить "зв'язок" між IoC 
   що насправді не пов'язані

```

**Провал 2: Contradictory Knowledge**
```
❌ Проблема: LLM змішує дані різних кампаній/груп

✅ Вирішення: RAG з конкретними звітами + 
"Посилайся ТІЛЬКИ на наданий контекст, 
не на своє попереднє навчання"
```

**Провал 3: Constrained Generalization**
```
❌ Проблема: Нові TTP не маппуються — LLM не знає їх

✅ Вирішення: 
"Якщо техніка не є в ATT&CK — опиши її
```

### Слайд 42 — Multi-step OSINT Pipeline

```python
class OSINTPromptPipeline:
    """
    Автоматизований OSINT-аналіз через серію промптів
    """
    
    def __init__(self, llm_client):
        self.llm = llm_client
        self.context = {}
    
    def step1_extract_entities(self, raw_text: str) -> dict:
        """Крок 1: Entity extraction"""
        prompt = f"""Витягни сутності з тексту. 
        Формат: JSON з полями PERSON, ORG, LOCATION, EMAIL...
        
        ТЕКСТ: {raw_text}"""
        
        result = self.llm.complete(prompt)
        self.context['entities'] = result
        return result
    
    def step2_verify_claims(self, entities: dict) -> dict:
        """Крок 2: Cross-verification"""
        prompt = f"""Маємо сутності: {entities}
        
        Для кожної — визнач:
        1. Чи можна верифікувати публічно?
        2. Яке джерело підтвердить?
        3. Confidence: A/B/C/D
        
        Формат: JSON"""
        
        return self.llm.complete(prompt)
    
    def step3_synthesize(self, verified: dict) -> str:
        """Крок 3: Аналітичний синтез"""
        prompt = f"""На основі верифікованих даних:
        {verified}
        
        Напиши executive summary (5-7 речень).
        Вкажи ключові висновки і gaps."""
        
        return self.llm.complete(prompt)
```

### Слайд 46 — 5 перевірок якості LLM-відповіді

**Перевірка 1: Double-Query**
```
Запит A: "Що ти знаєш про X?"
Запит B: "Чого ти НЕ знаєш про X?"
→ Порівняй: чи визнає LLM свої обмеження?
```

**Перевірка 2: Source Challenge**
```
"Перерахуй всі джерела для своїх тверджень.
Якщо джерела немає — позначи [UNSOURCED]."
→ Виявляє галюциновані факти
```

**Перевірка 3: Reverse Verification**
```
Надай відповідь LLM назад і спитай:
"Знайди помилки в цьому тексті."
→ LLM часто знаходить власні помилки
```

**Перевірка 4: Confidence Calibration**
```
"Оціни впевненість у кожному твердженні від 0 до 1.
Для всього < 0.7 — вкажи що потрібно перевірити."
```

**Перевірка 5: Alternative Hypothesis**
```
"Сформулюй найсильніший аргумент ПРОТИ 
твого основного висновку."
→ Антидот до підтвердження упередження
```

### Слайд 50 — Context Engineering: наступний рівень

**Context Engineering (2026) = Prompt + Memory + Tools + State**

```python
class OSINTContextEngine:
    def __init__(self):
        self.memory = {}          # Що ми вже знаємо
        self.tools = []           # Доступні інструменти  
        self.investigation_state = {}  # Поточний стан
        
    def build_context(self, query: str) -> str:
        return f"""
ПОСТІЙНА ПІСОЧНИЦЯ:
Ти — Senior OSINT Analyst. Ти працюєш 
над розслідуванням: {self.investigation_state['name']}

ЩО МИ ВЖЕ ЗНАЄМО:
{self._format_memory()}

ДОСТУПНІ ІНСТРУМЕНТИ:
{self._format_tools()}

ПОТОЧНИЙ СТАН РОЗСЛІДУВАННЯ:
- Фаза: {self.investigation_state['phase']}
- Підтверджено: {self.investigation_state['confirmed']}
- Gaps: {self.investigation_state['gaps']}

ЗАПИТ АНАЛІТИКА:
{query}
"""
```

**Результат:** LLM "пам'ятає" все розслідування і діє як колега, а не Oracle

### Матриця вибору CoT-підходу

| Задача | CoT тип | Приклад команди |
|--------|---------|----------------|
| Просте питання | Без CoT | "Витягни email з тексту" |
| Аналіз документу | Standard CoT | "Думай крок за кроком" |
| Attribution | Layered CoT | "3 проходи: факти → протиріччя → висновок" |
| Верифікація фото | Structured CoT | "КРОК 1: ... КРОК 2: ..." |
| Аналіз масивного витоку | LongRePS | "Це великий документ. Спочатку резюме, потім деталі..." |
| Перевірка висновку | Self-consistency | "Дай 3 різних відповіді, потім обери найімовірнішу" |
